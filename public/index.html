The problem

When you pay online, the shop usually doesn't see your card. A payment company handles the money, then sends the shop a short message: this order was paid. The shop ships on the strength of that message. If the shop doesn't check it carefully, a made-up, repeated or altered message can cost real money.

Paid too little

An order is marked paid for less than it cost.

Shipped twice

One payment is counted again and the goods go out twice.

Order lost

The customer paid, but the shop never finds out.

Wrong account

A payment is credited to somebody else's order.

Refund mismatch

Money is refunded but the order still counts as paid.

What we do

We build checkouts in our own lab, send them the kinds of bad messages an attacker would, and measure what happens to the money and the orders.

  • Forged a message the provider never sent
  • Replayed a real message sent again
  • Reordered real messages in the wrong order
  • Mismatched the right message for the wrong order or amount

  1. Build a careful reference

    A checkout we wrote ourselves that handles every case correctly, plus copies with one deliberate mistake each. They prove our tests can tell safe from unsafe.

  2. Attack it locally

    Every test runs on our own computers against software we own or run ourselves. No real shop, card or customer is involved.

  3. Measure the harm

    We record what went wrong in money and orders, and give each checkout an assurance score that keeps anything we couldn't test visible rather than assuming it passed.

Roadmap

Six stages, from the measuring tools to a published paper.

  1. Foundation

    Project structure, automated checks and the written rules the research follows.

  2. Measuring tools

    The reference checkout, the tests that attack it, and the way harm is counted.

  3. Realism

    Local stand-ins that speak the same message formats as real payment providers.

  4. Pilot

    A small trial run, then the study plan is published before the main run begins.

  5. Main study

    The full set of tests. Anything found in open-source software is reported privately to its maintainers first.

  6. Release

    The paper, a free tool for checking your own checkout, and the data.

How we keep it safe

Only our own software

We test software we wrote or open-source software we run on our own machines. We never probe a live shop or payment system we don't own.

No real money or card data

Every order, payment and customer in the lab is made up. Nothing is charged and nothing is shipped.

Fix first, publish second

If we find a weakness in someone else's open-source software, its maintainers hear about it privately before anything is published.

The assurance score is a research measure. It is not a PCI certification or a guarantee that a checkout is secure.
