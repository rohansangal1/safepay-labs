# Payment Integration Lab

**Do AI coding agents build safe payment integrations?** This project measures it. Agent-built Stripe and Square integrations are attacked with forged, replayed and mismatched payment events. The damage is measured in money and order state, and each integration is scored with **PIAS**, an evidence-aware assurance score that keeps unchecked controls visible instead of counting them as passes.

Status: research in progress, targeting a preprint. PIAS v0.1 is a draft metric, not a PCI assessment or a probability of compromise. See the [research plan](docs/RESEARCH_PLAN.md).

## Setup
Requires **Node.js 22.13+** (24 recommended, see `.nvmrc`) and Python 3 for the local site server. No provider keys are needed.

```sh
npm ci
npm test              # engine and reference-checkout tests
npm run typecheck     # TypeScript type check (Node runs the .ts files directly)
npm run assess        # assess the reference checkout → data/runs/lab-reference.json
npm run site          # build and serve the site at http://127.0.0.1:4173
```

The code is TypeScript that Node runs directly through type stripping. `.npmrc` enables it for every npm script, so there's no build step ([ADR 004](docs/decisions/004-typescript-type-stripping.md)).

## The website
`npm run site` copies the engine and the latest results into `site/` and serves it. Press `Ctrl+C` to stop. The site must be served over HTTP; opening `index.html` from disk won't load its data.

| File | Controls |
|---|---|
| `site/data/milestones.json` | Roadmap board and progress (`not-started`, `in-progress`, `done`) |
| `site/data/library.json` | Research library entries |

`site/score.js`, `site/data/controls.json` and `site/data/assessments.json` are generated by `npm run build:site`. Don't edit them. The site's F-fixtures are synthetic illustrations; lab runs are real checks against the reference checkout.

## Reference checkout
`lab/subjects/reference/` is a small local checkout with a catalog, orders, payments and fulfillment records. It binds to 127.0.0.1 only and makes no outbound calls. There's no real provider, money or card data. It calibrates the checks: a known-good subject plus variants with one safeguard removed.

State lives in `node:sqlite`. A verified success event records the payment and a fulfillment job in one transaction; the job then runs from that outbox. If fulfillment fails or the process stops, the job stays pending and runs on the next event or restart. Unique indexes allow one fulfillment per order, however many events arrive.

`npm run assess` runs the 19 registered checks in `packages/checks` through the checkout's `SubjectAdapter` ([adapter.ts](lab/subjects/reference/adapter.ts)). They map to six PIAS controls (amount, binding, authenticity, fulfillment, authorization, idempotency). Each check is versioned and records its observation layer and oracle; the webhook checks read the checkout's fulfillment records, not its HTTP responses. A check that can't run leaves its control unknown, never passed. The baseline passes all six. It's rated *insufficient evidence* because the other six controls have no checks yet. Each of the seven seeded defects (`DEFECTS` in `app.ts`) is caught by its own control and no other, and the tests enforce this.

To explore by hand:
```sh
LAB_WEBHOOK_SECRET=devsecret npm run checkout            # http://127.0.0.1:4280
curl -X POST localhost:4280/orders -H 'x-lab-customer: alice' \
  -H 'content-type: application/json' -d '{"items":[{"sku":"lab-mug","qty":2}]}'
LAB_WEBHOOK_SECRET=devsecret npm run checkout:event -- ord_0001 alice
curl localhost:4280/orders/ord_0001 -H 'x-lab-customer: alice'   # status: fulfilled
```
Add `LAB_DEFECTS=skipSignature` (comma-separated) to start it with a seeded defect. Add `LAB_DB=work/checkout.db` to keep state across restarts (`work/` is git-ignored).
